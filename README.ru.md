<h1 align="center">pi-offline-engine</h1>

<p align="center"><b>Сделайте разработку на локальных моделях практичной: офлайн-расширение для агента Pi, которое объединяет проверку готовности, ограниченное делегирование рутинных правок крошечной локальной модели с проверкой настоящими сборкой и тестами .NET, экономию контекста и вывода инструментов, закреплённый сопутствующий набор инструментов и необязательный сбор обучающих данных — всё на вашей машине.</b></p>

```bash
pi install git:github.com/AndrewMoryakov/pi-offline-engine
llama-server -m qwen2.5-coder-3b-instruct-q4_k_m.gguf   # the tiny implementer, listens on :8080
pi                                                      # then run /offline-doctor
```

`pi-offline-engine` — это пакет расширений Pi для работы с **локальными** языковыми моделями, в том числе совсем без сети. Одна установка приносит движок и четыре закреплённых сопутствующих расширения (поиск, языковой сервер, code tool, lean edit). Поверх них движок добавляет: доктор готовности и автообнаружение endpoint при первом запуске; два инструмента делегирования, которые передают точно описанное изменение гораздо меньшей локальной модели для кода и позволяют настоящим `dotnet build` / `dotnet test` решить, получилось ли оно; детерминированный снимок репозитория и сжатие большого вывода сборки, чтобы медленная модель тратила меньше токенов; урезанный набор инструментов для медленных моделей; локальную телеметрию; и необязательный рекордер, превращающий проверенные попытки в обучающие данные.

Проект экспериментальный (версия 0.0.16, Git-распространяемый пакет Pi, не опубликован в npm), а проверка сегодня **только для .NET**. Раздел [«Статус и известные ограничения»](#статус-и-известные-ограничения) точно говорит, что измерено, а что нет.

## Простыми словами

### Проблема

Агент для кода на локальной модели привлекателен: ваш код остаётся на вашей машине, и он продолжает работать в самолёте. Но лучшие локальные модели большие и медленные. Каждый рутинный шаг — небольшая правка, сборка, упавший тест, ещё одна правка — стоит медленного хода, забивает контекстное окно модели выводом компилятора и даёт большой модели много возможностей уйти не туда. К тому же у локальной конфигурации больше подвижных частей, чем у хостовой: какой сервер, какая модель, какой поиск, какой языковой сервер — и «будет ли это работать, когда я отключусь от сети?».

### Для кого

Для разработчиков, которые используют агент Pi с локальной основной моделью (часто медленной), нередко на коде .NET, нередко офлайн или вот-вот будут офлайн. Продвинутые пользователи могут настраивать локальный сервер, инструменты правки и бюджет контекста, а также собирать данные для обучения модели поменьше.

### Что вы получаете

- **Настройку, которая работает из коробки.** Одна команда `pi install` приносит движок и четыре сопутствующих расширения с точными закреплёнными версиями. При первом запуске движок ищет локальный OpenAI-совместимый сервер и сохраняет его; `/offline-doctor` говорит, готовы ли вы, пока сеть ещё есть.
- **Более дешёвые ходы.** Большая модель пишет одну строгую спецификацию ограниченного изменения; крошечный локальный кодер предлагает патч; движок применяет его точно, запускает объявленные `dotnet build` и тесты и отправляет компактную сводку сбоя обратно крошечному кодеру — а не большой модели — для до двух починок.
- **Меньшую поверхность, видимую модели.** Большой вывод `dotnet build` / `dotnet test` сжимается до попадания к модели, добавляется небольшой снимок Git, чтобы первые ходы не уходили на ориентацию, а `/offline-tools minimal` урезает список инструментов для медленных моделей.
- **Узкую зону поражения.** Вы один раз одобряете объявленный набор файлов; записи точные и проверяются по области, файл, изменившийся за это время, отклоняется, а решают результаты компилятора и тестов, а не мнение модели.
- **Локальные свидетельства.** Телеметрия, полные логи сборки и записи кандидатов остаются в каталоге `.pi/offline-engine/`, который игнорируется git, а проверенные попытки можно по желанию сохранять как обучающие данные.

### Чем проект не является

- Это не универсальный кодер для любого стека: проверка запускает только `dotnet build` / `dotnet test`, а другие инструментальные цепочки в репозитории не описаны.
- Это не замена ревью: `verification_passed` означает лишь, что объявленные проверки компилятора и тестов прошли, а не что задача решена по смыслу. Основной агент должен просмотреть diff.
- Это не песочница файловой системы. Одобренный набор файлов ограничивает то, что может записать *кандидат*; `dotnet build` и `dotnet test` затем запускаются в вашем репозитории с вашими правами и могут создавать файлы (например, в `bin`/`obj`) или выполнять хуки сборки и тестов проекта.
- Это не офлайн, если указать крошечному исполнителю хостовый роутер. Это возможно, но [это не офлайн-конфигурация](#хостовые-openai-совместимые-роутеры-openrouter).
- Это пока не измерено на настоящей локальной модели: у приёмочного прогона с реальной моделью нет записанного результата (см. [статус](#статус-и-известные-ограничения)).

### Глоссарий

| Термин | Значение здесь |
|---|---|
| **Pi** | Терминальный coding-агент, который расширяет этот пакет (npm-пакет `@earendil-works/pi-coding-agent`). Расширения добавляют инструменты, команды и хуки. |
| **Основная модель** | Большая медленная локальная (или хостовая) модель, с которой вы общаетесь в Pi; она рассуждает, планирует и решает, когда работа закончена. |
| **TinyCoder / крошечный исполнитель** | Гораздо меньшая модель за любым OpenAI-совместимым endpoint (например, кодовая GGUF на 3B в `llama-server`), которая лишь выдаёт ограниченные патчи. |
| **ImplementationSpec** | Строгий JSON, который пишет основная модель: цель, требования, разрешённые файлы (не более двух) и сборка/тесты для запуска. |
| **Кандидат (candidate)** | Предложенный TinyCoder патч: точные правки `replace_text` или явно разрешённый `create_file`. |
| **Исходное состояние / проверка устаревания** | SHA-256 каждого разрешённого файла, снимаемый перед каждой попыткой; кандидат отклоняется, если любой из этих файлов изменился до применения. |
| **RepairPacket** | Компактное описание неудачной попытки (что изменено, выбранные диагностики, ссылки на логи), отправляемое TinyCoder. |
| **Эскалация (`needs_main_model`)** | Результат, возвращаемый, когда дешёвый цикл не может завершиться; управление возвращается основной модели. |
| **Капсула** | Небольшой детерминированный снимок Git, подставляемый как данные перед запуском агента. |
| **TRX** | Формат файла результатов тестов, который движок требует как свидетельство того, что тесты действительно выполнялись. |

## Что внутри

Метки статуса: без метки — реализовано в этом репозитории; **experimental (экспериментально)** — реализовано, но мало испытано или не измерено от начала до конца; **optional / deferred / planned (необязательно / отложено / запланировано)** — не входит в установку по умолчанию.

### Ограниченное делегирование (основной цикл)

- **Два инструмента Pi.** `delegate_implementation` возвращает кандидата и ничего не записывает; `execute_delegated_implementation` выполняет весь ограниченный цикл. → [Делегирование подробно](#текущий-вертикальный-срез)
- **Строгий `ImplementationSpec` v1.** Одна операция (`modify_symbol`), целевой файл и символ, требования, необязательный список `preserve`, разрешённый набор файлов не более двух и проверка для запуска. → [ImplementationSpec v1](#implementationspec-v1)
- **Точные защищённые записи.** `replace_text` (ожидаемый текст должен встречаться ровно один раз) и явно разрешённый `create_file` — после проверок SHA-256 исходного состояния, устаревания и символических ссылок, через очередь файловых мутаций Pi. → [Безопасность](#безопасность)
- **Детерминированная проверка .NET.** Движок сам строит команды `dotnet build` / `dotnet test` (модель не может внедрить команду оболочки), с `--no-restore`, и требует свидетельство TRX, что тесты выполнялись. → [Проверка](#проверка)
- **Дешёвая починка, затем эскалация.** До двух починок (всего три попытки) через компактный `RepairPacket`; некорректный или не-JSON вывод модели повторяется тем же способом; всё нерешённое возвращает `needs_main_model`. → [Починка и эскалация](#починка-и-эскалация)

### Готовность к офлайну

- **`/offline-doctor`.** Проверяет endpoint и модель TinyCoder, локален ли этот endpoint, `dotnet`, режим раннера `dotnet test`, игнорируется ли `.pi/offline-engine/` в git, необязательный `csharp-ls` и какие сопутствующие инструменты загружены. → [Офлайн-эксплуатация](#офлайн-эксплуатация)
- **Автообнаружение при первом запуске и `/offline-setup`.** Опрашивает loopback-порты `8080`, `8081`, `1234` (LM Studio) и `11434` (Ollama) и сохраняет первый сервер с chat-моделью. → [Крошечный исполнитель](#крошечный-исполнитель-tiny-implementer)
- **`/offline-status`.** Показывает каждую действующую настройку и откуда она взята: из окружения, из сохранённой конфигурации или по умолчанию.
- **Офлайн-чеклист.** Что скачать, проиндексировать и восстановить, пока сеть ещё есть. → [Рекомендуемый офлайн-стек для .NET](#рекомендуемый-офлайн-стек-для-net)
- **Хостовый роутер как вариант.** Слот крошечного исполнителя принимает и хостовый OpenAI-совместимый роутер, например OpenRouter; доктор помечает это как неофлайн-конфигурацию. → [Хостовые роутеры](#хостовые-openai-совместимые-роутеры-openrouter)

### Меньше токенов для медленных моделей

- **Сжатие результатов инструментов.** Большой вывод оболочки для прямого `dotnet build` / `dotnet test` превращается в выбранные диагностики плюс путь к полному логу. `/offline-compact`. → [Сжатие результатов инструментов](#сжатие-результатов-инструментов)
- **Капсула контекста репозитория.** Ограниченный снимок Git (корень, ветка, HEAD, отслеживаемые изменённые файлы, отслеживаемые `.sln`/`.slnx`/`.csproj`/`global.json`), подставляемый перед запуском агента. `/offline-context`. → [Капсула контекста репозитория](#капсула-контекста-репозитория)
- **Минимальный набор инструментов.** `/offline-tools minimal` оставляет только нужные медленной модели инструменты, а `restore` возвращает прежний набор. → [Офлайн-эксплуатация](#офлайн-эксплуатация)
- **Локальная телеметрия.** `/offline-stats` сводит вызовы TinyCoder, токены, задержки, результаты проверок, repair packet'ы и число символов, не попавших в контекст модели. → [Файлы на диске](#файлы-на-диске)

### Сопутствующий стек (встроенный, закреплённый)

- **pi-knowledge** (локальный поиск), **pi-lsp-extension** (семантика языкового сервера с запасным Tree-sitter), **pi-code-tool** (Python в песочнице поверх инструментов), **pi-lean-edit** (диапазонные правки на основе снимков). Все четыре закреплены на точных версиях и загружаются через манифест этого пакета. → [Сопутствующий стек](#рекомендуемый-офлайн-стек-для-net)
- **Управление поставщиком `edit`.** `editProvider`: `lean` (по умолчанию), `none` или `hybrid` (edit из pi-lean-edit становится `line_edit` рядом с `edit` другого пакета), плюс `scriptEditPolicy`. → [Другой пакет, переопределяющий `edit`](#другой-пакет-переопределяющий-edit)
- **Правило «только чтение» для code tool.** Когда инструмент `code` активен, движок добавляет подсказки для модели, удерживающие его в режиме чтения; изменения идут через инструменты edit/write верхнего уровня или `execute_delegated_implementation`.
- **Необязательное / отложенное.** `pi-sub-agent` (необязательно) и `pi-tree-sitter` (отложено) ставятся только по запросу через скрипт начальной настройки.

## Как это работает

Движок — это одно расширение Pi (`extensions/index.ts`) поверх не зависящего от Pi ядра в `src/`. Оно добавляет два инструмента, восемь слэш-команд и несколько хуков событий и загружает рядом с собой четыре сопутствующих расширения.

### Цикл делегирования

1. **Большая модель планирует.** Она пишет строгий `ImplementationSpec` — область, требования и сборку/тесты для запуска — а вы один раз одобряете объявленные файлы.
2. **Крошечный кодер предлагает патч.** Движок снимает SHA-256 каждого разрешённого файла, затем просит локальный TinyCoder о кандидате; если информации не хватает, он должен вернуть `insufficient_spec`, а не гадать, и может вернуть `cannot_safely_implement`.
3. **Движок применяет и проверяет.** Кандидат валидируется, проверяется на устаревание и применяется точно, затем запускаются `dotnet build` и тесты с `--no-restore`.
4. **Красное — это починка, а не поход к большой модели.** Компактный `RepairPacket` уходит к TinyCoder, до двух починок; зелёный результат даёт свидетельство `verification_passed`, а всё ещё красный — эскалацию основной модели.

## Быстрый старт

## Установка

Одна команда устанавливает движок **и** его сопутствующий стек:

```bash
pi install git:github.com/AndrewMoryakov/pi-offline-engine
```

Для воспроизводимых установок в команде или в дороге используйте проверенный тег релиза или коммит вместо движущейся ветки по умолчанию:

```bash
pi install git:github.com/AndrewMoryakov/pi-offline-engine@<release-tag-or-commit>
```

Это Git-распространяемый пакет Pi (`private: true`); он не опубликован в npm. Проверенная базовая версия хоста — **Pi 0.86.1** на **Node.js 22.19.0 или новее**. Пакет держит модули ядра Pi как peer-зависимости `"*"`, как того требует загрузчик пакетов Pi, а разработка и CI закрепляют Pi 0.86.1 для воспроизводимых интеграционных тестов.

pi клонирует репозиторий и запускает `npm install`, который подтягивает четыре встроенных сопутствующих расширения — `pi-knowledge`, `pi-lsp-extension`, `pi-code-tool`, `pi-lean-edit` — с точными закреплёнными версиями, все они загружаются через манифест этого пакета. См. [docs/OFFLINE_PROFILE.md](docs/OFFLINE_PROFILE.md), что делает каждое из них и какие необязательные пакеты остаются по желанию. Не выполняйте `pi install` для этих четырёх по отдельности: это зарегистрирует дублирующиеся инструменты.

### Другой пакет, переопределяющий `edit`

pi-lean-edit регистрирует `read`, `edit` и `write`. Pi отказывается стартовать, когда два расширения регистрируют одно и то же имя инструмента, поэтому пакет со своим `edit` — например `git:github.com/sting8k/pi-utils` — останавливает pi с ошибкой `Tool "edit" conflicts with ...`. Pi не показывает расширениям инструменты других пакетов на время их загрузки, так что движок не может решить это сам; выберите одного поставщика или запустите оба рядом:

- оставьте pi-lean-edit и отключите другой — для pi-utils добавьте `"edit"` в `disabledTools` в `~/.pi/agent/pi-utils.json`;
- либо оставьте другой и задайте `"editProvider": "none"` в конфигурации движка ниже (или `PI_OFFLINE_EDIT_PROVIDER=none`). `read` и `write` из pi-lean-edit уходят вместе с ним, поскольку его `edit` принимает только диапазоны, которые показал его собственный `read`.

- либо оставьте оба: задайте `"editProvider": "hybrid"` (или `PI_OFFLINE_EDIT_PROVIDER=hybrid`) и оставьте другой `edit` включённым. Тогда диапазонная правка pi-lean-edit регистрируется как `line_edit`, а другой пакет сохраняет `edit`.

`/offline-doctor` показывает, какое расширение предоставляет `edit` и, когда это не pi-lean-edit, что причина — `editProvider=none`. В гибридном режиме он называет источник обоих инструментов и то, предлагается ли сейчас `edit`.

#### Гибрид: какой edit видит модель

Постановка задачи с указанием, откуда взято каждое правило, — [docs/HYBRID_EDIT_V0.md](docs/HYBRID_EDIT_V0.md).

`scriptEditPolicy` (конфиг) или `PI_OFFLINE_SCRIPT_EDIT_POLICY` (окружение) определяет, когда другой `edit` предлагается рядом с `line_edit`:

- `always` (по умолчанию): предлагается всегда. Модель выбирает между двумя инструментами по их описаниям.
- `cloud-only`: скрыт, пока `baseUrl` модели сессии локальный (loopback, RFC1918, `.local`, голое имя хоста), и предлагается для удалённого. Пересчитывается при старте сессии и при каждой смене модели. Сильная модель, доступная через локальный адрес, например туннель на `127.0.0.1`, считается здесь локальной.
- `never`: зарегистрирован, но никогда не предлагается.

Скрытие `edit` не направляет модель к `line_edit`. В живом прогоне со скрытым скриптовым edit модель на 27B выполнила переименование в 11 файлах через `sed -i` в `bash`, у которого нет ни проверки устаревшего текста как у `line_edit`, ни diff и отката как у скриптового edit. Поэтому по умолчанию `always`; см. `HE-10` в постановке задачи.

Политика лишь убирает и возвращает сам `edit`; она никогда не включает обратно `edit`, который вы отключили, а `/offline-tools minimal` держит его скрытым. Инструменты, которые вызывают встроенные возможности Pi напрямую, например мост `pi-code-tool`, ей не подчиняются (см. [docs/OFFLINE_PROFILE.md](docs/OFFLINE_PROFILE.md)).

Схема edit в pi-lean-edit — объединение (union) без `properties` на верхнем уровне, и парсер вызовов инструментов в ik_llama.cpp возвращает аргументы такого инструмента пустыми. Поэтому движок отдаёт модели уплощённую схему в режимах `lean` и `hybrid`; недопустимые сочетания pi-lean-edit по-прежнему отклоняет сам. См. `HE-11`.

`npm run gate:edit` загружает pi-lean-edit рядом с фикстурным `edit` через установленный pi в каждом режиме и проверяет результат, в том числе что `lean` по-прежнему отклоняет такую пару.

## Текущий вертикальный срез

Цикл делегирования — ядро движка. Предоставлены два инструмента Pi:

- `delegate_implementation` — только кандидат; без записи.
- `execute_delegated_implementation` — ограниченный цикл реализации с защищёнными записями и детерминированной проверкой .NET.

Поток выполнения:

```text
main local model
  -> strict ImplementationSpec
  -> one user approval for the declared file scope
  -> local TinyCoder
  -> exact candidate validation + stale-preimage check
  -> apply
  -> dotnet build/tests --no-restore
  -> compact RepairPacket on failure
  -> TinyCoder repair (up to two)
  -> verification_passed evidence or escalation to main model
```

Основная модель не участвует в дешёвом цикле починки. Инструменты несут подсказки для основной модели: делегировать только после того, как решены архитектура и область, держать `allowed_files` не более чем на двух файлах, вставлять точный нужный исходный код в `context` (движок сам не читает файлы для TinyCoder, а крошечная модель — не исследователь репозитория) и вызывать `execute_delegated_implementation` как единственный изменяющий инструмент в своём ходе ассистента, чтобы параллельные записи не искажали проверку. Это инструкции для модели, а не принудительное ограничение.

### Починка и эскалация

- **Попытки.** Запуск делает не более 2 попыток починки после первой, то есть не более 3 попыток TinyCoder всего. `PI_OFFLINE_TINY_MAX_ATTEMPTS` (или сохранённый `maxAttempts`) может уменьшить это число; оно ограничено значением 3.
- **Починка при красном.** Когда сборка или объявленные тесты падают, компактный `RepairPacket` (пути и операции прежних изменений, статус сборки/тестов, выбранные диагностики, ссылки на артефакты) отправляется TinyCoder вместе с исходной спецификацией и контекстом.
- **Некорректный вывод модели.** Ответ, который не является корректным JSON или не проходит валидацию кандидата, повторяется через пакет `model_output_failure` в рамках того же бюджета попыток.
- **Что возвращается.** `verification_passed` (только свидетельство компилятора/тестов — основной агент всё равно должен просмотреть diff), собственные `insufficient_spec` / `cannot_safely_implement` от TinyCoder, когда ничего не изменено, либо `needs_main_model` с `reason`, например `tiny_implementation_attempts_exhausted`, `tiny_invalid_output`, `tiny_transport_failure`, `verification_infrastructure_failure`, `verification_execution_failure` или `candidate_apply_failure`, плюс стадия, изменялось ли рабочее дерево, и изменённые файлы.
- **Известная граница.** Если проверка остаётся красной после последней попытки, последний кандидат остаётся в рабочем дереве, а управление возвращается основной модели. Автоматического отката Git или устойчивого к сбоям транзакционного восстановления нет.
- **Без интерфейса (headless).** Изменяющее делегированное выполнение требует интерактивного подтверждения; без UI оно отклоняется, если не задан `PI_OFFLINE_ALLOW_HEADLESS_APPLY=1`, что предназначено только для отдельно изолированного рабочего процесса.

Контракт рантайма — в [docs/BOUND_DELEGATION_V0.md](docs/BOUND_DELEGATION_V0.md).

### Проверка

Команды строит движок, а не модель — из `verification.build.project` и `verification.tests.project`, всегда с `--no-restore`. Свидетельством тестов должен быть свежий файл TRX с числом выполненных тестов больше нуля; одного кода выхода 0 никогда не достаточно. Раннер тестов определяется для каждого репозитория:

- **VSTest:** каждый объявленный шаблон теста запускается отдельно через `--filter` и логирование TRX.
- **.NET 10 Microsoft.Testing.Platform (MTP):** набор тестов проекта запускается один раз с `--report-trx`, и каждый объявленный шаблон должен найтись среди выполненных идентификаторов тестов в TRX. Тестовый проект должен уже предоставлять `Microsoft.Testing.Extensions.TrxReport`, так что восстановите его, пока сеть ещё есть.

Предварительная проверка перед первым вызовом TinyCoder останавливается без продолжения (fail closed), если, например, активен MTP, но отчёты TRX недоступны. Полные stdout/stderr каждой проверки хранятся в `.pi/offline-engine/artifacts/`, а свежий результат TRX — в `.pi/offline-engine/test-results/`; через контекст модели отправляются только компактные диагностики.

## Крошечный исполнитель (Tiny implementer)

Endpoint и модель определяются в таком порядке: **переменная окружения > сохранённая конфигурация > встроенное значение по умолчанию** (`http://127.0.0.1:8080`, `qwen2.5-coder-3b-instruct`).

Сохранённая конфигурация лежит в `<pi agent dir>/pi-offline-engine/config.json` (обычно `~/.pi/agent/pi-offline-engine/config.json`; `PI_CODING_AGENT_DIR` учитывается). В ней никогда не хранятся ключи API. Управляйте ею так:

```text
/offline-setup                          # re-run discovery; asks which one if several servers answer
/offline-setup http://127.0.0.1:9000    # explicit endpoint, verified before it is saved
/offline-setup http://127.0.0.1:9000 my-model
/offline-setup reset                    # forget the saved endpoint/model
```

Каждая настройка завершается отчётом `/offline-doctor`. Переменные окружения по-прежнему главнее сохранённой конфигурации — это удобно для скриптов и разовых запусков:

```bash
export PI_OFFLINE_TINY_ENDPOINT=http://127.0.0.1:8081
export PI_OFFLINE_TINY_MODEL=qwen2.5-coder-3b-instruct
export PI_OFFLINE_TINY_MAX_ATTEMPTS=3
```

Если endpoint включает префикс пути обратного прокси, этот префикс сохраняется при разрешении `health`, `v1/models` и `v1/chat/completions`.

`/offline-status` показывает действующие настройки и откуда взято каждое значение (окружение, файл конфигурации или значение по умолчанию), локальный ли endpoint и настроен ли ключ.

Исполнитель запрашивает структурированный вывод через `response_format: json_schema` (строгий; необязательные поля передаются как обязательные, но допускающие null, чтобы строгие валидаторы, по замыслу, принимали схему — на живом хостовом endpoint это ещё не проверено на живом хостовом endpoint; после разбора null снова отбрасываются). llama-server (llama.cpp и ik_llama.cpp) поддерживает его, компилируя схему в грамматику; если это преобразование не удаётся, сервер отвечает HTTP 500 с `JSON schema conversion failed`, и движок один раз повторяет запрос с `json_object`. Тот же единственный повтор применяется, когда сервер или роутер сообщает, что схема или `response_format` не поддерживается или недопустим. Сэмплирование идёт с `temperature: 0`, а у каждого запроса к TinyCoder в текущем коде тайм-аут 120 секунд.

### Хостовые OpenAI-совместимые роутеры (OpenRouter)

Слот исполнителя принимает любой OpenAI-совместимый endpoint. Хостовый роутер отличается лишь тем, что требует bearer-токен, поэтому переключателя провайдера нет — задайте ключ, и заголовок `Authorization` будет отправлен:

```bash
export PI_OFFLINE_TINY_ENDPOINT=https://openrouter.ai/api/v1
export PI_OFFLINE_TINY_MODEL=qwen/qwen3-coder-30b-a3b-instruct
export PI_OFFLINE_TINY_API_KEY=sk-or-v1-...   # OPENROUTER_API_KEY is also honoured
```

Используйте точный id модели из `https://openrouter.ai/api/v1/models`; `/offline-doctor` сверяет настроенный id с этим каталогом. У OpenRouter нет `/health`, поэтому доступность определяется только каталогом моделей.

Проверьте настоящий ключ от начала до конца, не трогая репозиторий:

```bash
node scripts/smoke-tiny-transport.mjs --live
```

**Это не офлайн-конфигурация.** Промпты, текст спецификации и фрагменты исходного кода из `context.relevant_source` отправляются третьей стороне и далее тому провайдеру, который обслуживает модель. `/offline-doctor` сообщает об этом как о предупреждении `endpoint_locality` с названием принимающего хоста; это предупреждение, а не отказ готовности, потому что конфигурация выбрана намеренно. Учтите, что проверка локальности проводит границу по вашей сети, а не по этой машине — loopback, адреса RFC1918 и голые имена хостов считаются локальными, поэтому сервер в локальной сети не помечается.

Ключ отправляется только как заголовок `Authorization`. Он не записывается в `events.jsonl`, записи кандидатов или обучающие данные, а тело ответа `401`, цитирующее ключ, редактируется перед сохранением. Редактирование по-прежнему касается только того, что этот движок пишет на диск, — оно ничего не говорит о том, что роутер делает с отправленным ему исходным кодом.

## ImplementationSpec v1

Пример:

```json
{
  "version": 1,
  "spec_id": "retry-001",
  "operation": "modify_symbol",
  "goal": { "summary": "Propagate cancellation into the retry delay." },
  "target": {
    "file": "src/Payments/RetryPolicy.cs",
    "symbol": "RetryPolicy.ExecuteAsync"
  },
  "requirements": [
    "Call ThrowIfCancellationRequested before every retry.",
    "Pass cancellationToken to Task.Delay."
  ],
  "scope": {
    "allowed_files": ["src/Payments/RetryPolicy.cs"],
    "allow_new_files": false,
    "allow_dependencies": false,
    "allow_public_api_change": false
  },
  "verification": {
    "build": { "project": "src/Payments/Payments.csproj" },
    "tests": {
      "project": "tests/Payments.Tests/Payments.Tests.csproj",
      "names": ["RetryPolicyTests.CancellationBeforeRetry"]
    }
  }
}
```

Делегирование v1 намеренно ограничено не более чем двумя файлами. В v1 `operation` должна быть `modify_symbol`, `target.file` должен входить в `scope.allowed_files`, а необязательный массив `preserve` из непустых строк указывает, что менять нельзя. Вызов инструмента принимает также необязательный объект `context`, в котором основная модель передаёт точный исходный код, нужный TinyCoder.

## Формат кандидата

Авто-применение поддерживает только точные операции:

```json
{
  "status": "candidate",
  "changes": [
    {
      "path": "src/Payments/RetryPolicy.cs",
      "operation": "replace_text",
      "expected": "await Task.Delay(delay);",
      "content": "await Task.Delay(delay, cancellationToken);"
    }
  ]
}
```

либо явно разрешённый `create_file` (спецификация должна разрешать новые файлы, а путь должен быть в `scope.allowed_files`).

Если TinyCoder не хватает информации, он должен вернуть `insufficient_spec`, а не гадать; `cannot_safely_implement` — третий допустимый статус. Символические ссылки и пути вне рабочей области или набора файлов отклоняются. Более семантические операции, такие как `replace_symbol`, не реализованы; им понадобится более поздний срез на основе Tree-sitter/Roslyn.

## Безопасность

Перед каждой попыткой TinyCoder снимается SHA-256 для каждого разрешённого файла. Кандидат отклоняется как устаревший, если любой из этих файлов изменился до применения.

Мутации используют очередь файловых мутаций Pi, проверяются по области и требуют интерактивного подтверждения, если только `PI_OFFLINE_ALLOW_HEADLESS_APPLY=1` не включён явно в контролируемой песочнице.

Полные логи проверки и записи кандидатов остаются в каталоге `.pi/offline-engine/`, который игнорируется git. Проверка тестов учитывает раннер: VSTest использует целевые запуски TRX, а .NET 10 Microsoft.Testing.Platform использует `--report-trx` и сверяет объявленные шаблоны с выполненными идентификаторами TRX.

| Движок гарантирует | Движок не гарантирует |
|---|---|
| Кандидат затрагивает только файлы из одобренной области — точной заменой или явно разрешённым созданием | Песочницу файловой системы: `dotnet build` / `dotnet test` запускаются в вашем репозитории с вашими правами и могут создавать файлы (например, `bin`/`obj`) или выполнять хуки сборки/тестов проекта |
| Файл, изменившийся после снимка, не перезаписывается | Что `verification_passed` означает смысловую готовность задачи — основной агент должен просмотреть diff |
| Модель не может внедрить команду проверки | Откат после всё ещё красной последней попытки |
| Ключ API никогда не попадает в файл конфигурации, `events.jsonl`, записи кандидатов или обучающие данные | Что хостовый роутер делает с отправленным ему исходным кодом |
| Сбор обучающих данных выключен, пока вы его не включите | Что экспортированный набор данных безопасно публиковать — сначала просмотрите его |

## Офлайн-эксплуатация

Перед отключением от сети:

```text
/offline-doctor
```

проверяет настроенный endpoint/модель TinyCoder, локален ли этот endpoint, `dotnet` и режим раннера `dotnet test` (VSTest или MTP с TRX), игнорируется ли `.pi/offline-engine/` в Git, необязательный `csharp-ls`, а также то, содержит ли текущий загруженный набор инструментов Pi ожидаемые возможности поиска/LSP/code-mode/структурной навигации и поставщика `edit`. Endpoint TinyCoder, `dotnet` и инструмент `execute_delegated_implementation` обязательны; остальное — предупреждения.

Если `.pi/offline-engine/` не игнорируется, доктор советует добавить `/.pi/offline-engine/` в `.git/info/exclude` репозитория, чтобы локальные артефакты случайно не попали в индекс.

Для медленных локальных моделей уменьшите схему инструментов, открытую модели:

```text
/offline-tools minimal
```

Профиль предпочитает `code`, `knowledge_search` и инструменты LSP, если они установлены. Если их нет, он сохраняет встроенные запасные `grep/find/ls` Pi, а инструменты навигации по символам заменяют инструменты LSP. Остаются `read`, `edit`/`line_edit`, `write`, один shell-инструмент и два инструмента делегирования.

Восстановите прежний набор инструментов так:

```text
/offline-tools restore
```

`/offline-tools status` перечисляет, что модель может вызвать прямо сейчас. Полный чеклист «перед поездкой» — в [docs/OFFLINE_PROFILE.md](docs/OFFLINE_PROFILE.md).

## Сжатие результатов инструментов

Большие выводы оболочки `dotnet build` и `dotnet test` сжимаются до попадания в контекст модели.

Полный вывод сохраняется в:

```text
.pi/offline-engine/tool-results/
```

Модель получает выбранные диагностики компилятора/тестов (до 50 строк), небольшой хвост, если диагностик не найдено, и путь к артефакту.

Сжатие включено по умолчанию только для больших (8 000 символов и более) результатов одной прямой команды `dotnet build` / `dotnet test`, выполненной через shell-инструмент; конвейеры и составные команды остаются нетронутыми. Управляйте им так:

```text
/offline-compact on
/offline-compact off
/offline-compact status
```

или задайте `PI_OFFLINE_COMPACT_TOOL_RESULTS=0` перед запуском Pi.

## Капсула контекста репозитория

Перед запуском агента с локальной моделью pi-offline-engine может подставить небольшой детерминированный снимок Git:

- корень репозитория;
- текущая ветка и HEAD;
- отслеживаемые изменённые файлы;
- отслеживаемые файлы `.sln`, `.slnx`, `.csproj` и `global.json`.

Это избавляет от траты первых ходов модели на базовую ориентацию в репозитории. Снимок ограничен по размеру (перечисляются не более 30 изменённых файлов и 30 файлов проектов), хранится как данные, а не инструкции, и в контекст модели отправляется только последняя капсула. Она отправляется заново, только когда факты изменились, после сжатия сессии или после перехода по дереву сессии.

Она включена по умолчанию. Управляйте ею так:

```text
/offline-context on
/offline-context off
/offline-context refresh
/offline-context status
```

Установите `PI_OFFLINE_REPO_CAPSULE=0`, чтобы отключить её при запуске.

## Сбор обучающих данных

Проверенные попытки TinyCoder можно локально сохранять для будущего SFT, обучения на предпочтениях и оценки. Единица сбора — ограниченная транзакция реализации (спецификация, ограниченный контекст, необязательный RepairPacket, кандидат, метка проверки), а не стенограмма чата.

Сбор **выключен по умолчанию**:

```text
/offline-training on
/offline-training status
/offline-training export
/offline-training off
```

`/offline-training export` (или `npm run training:export`) записывает `sft.jsonl`, `unpaired-preference.jsonl`, `paired-preference.jsonl` (только когда корпус содержит и проверенного, и неудачного кандидата для в точности одного и того же промпта), `eval.jsonl` и манифест в `.pi/offline-engine/training/export/`. Пути, похожие на секретные (`.env*`, файлы учётных данных/секретов, приватные ключи), пропускаются, строки по возможности редактируются, а точные дубликаты отбрасываются; экспорт — это защитный фильтр, а не гарантия.

Прочитайте [docs/TRAINING_DATA.md](docs/TRAINING_DATA.md) перед включением: сырые трассы могут содержать приватный исходный код.

## Канонический локальный гейт

В репозитории настроен запуск релизных гейтов в GitHub Actions при пушах и pull request (их текущее состояние см. в [статусе](#статус-и-известные-ограничения)). Запустите те же проверки локально, начиная с:

```bash
npm ci
npm run gate:local
npm audit --omit=dev --audit-level=high
```

`gate:local` проверяет синтаксис, запускает модульные тесты, выполняет пробный запуск начальной настройки офлайн-профиля и запускает дымовой тест транспорта TinyCoder на встроенном в процесс HTTP-сервере.

Дерево production сейчас переопределяет `sharp` на проверенный релиз 0.35.4, потому что последний `pi-knowledge` всё ещё тянет затронутый релиз 0.34.x через `@huggingface/transformers`. Lock-файл и тесты упаковки обеспечивают это переопределение; не убирайте его, пока upstream-зависимость не догонит.

Он рассчитан на запуск без внешнего доступа к сети. Затем выполните:

```bash
npm run gate:pi
```

чтобы загрузить расширение через реально установленный рантайм Pi без запроса к LLM. Он управляет `pi --mode rpc` и требует, чтобы команды движка были зарегистрированы, поэтому расширение, которое падает при загрузке, проваливает гейт. См. [docs/LOCAL_VALIDATION.md](docs/LOCAL_VALIDATION.md).

`gate:pi` загружает только движок, так что не видит конфликта с другим пакетом. Для этого выполните:

```bash
npm run gate:edit
```

Он загружает `extensions/pi-lean-edit.ts` рядом с фикстурой, регистрирующей собственный `edit`, в каждом режиме `editProvider`, и падает, если `lean` перестаёт отклонять такую пару или если `none`/`hybrid` не загружаются, как описано выше.

Чтобы проверить весь путь «под ключ» — тот же `npm install --omit=dev`, который pi запускает для git-пакета, затем `pi install` во временный каталог агента, затем `/offline-doctor` по RPC с проверкой, что встроенные сопутствующие инструменты активны, — выполните (шаг npm требует сети; ваш собственный `~/.pi` не затрагивается):

```bash
npm run gate:install
```

## Первый реальный приёмочный прогон

В комплект входит контролируемая одноразовая фикстура .NET, чтобы первый запуск TinyCoder проверял конвейер, а не произвольный репозиторий.

Подготовьте её, пока есть сеть:

```bash
npm run acceptance:prepare -- --restore
```

Затем следуйте [docs/ACCEPTANCE_V0.md](docs/ACCEPTANCE_V0.md). В фикстуре одна локализованная ошибка; она нужна, чтобы испытать весь конвейер делегирования, а не чтобы измерять интеллект кодирования.

## Справочник

| `/offline-tools [status \| minimal \| restore]` | Урезать набор инструментов, видимый модели, для медленных моделей или восстановить его |
| `/offline-context [status \| on \| off \| refresh]` | Управление капсулой контекста репозитория |

## Диагностика неполадок

| Симптом | Вероятная причина и решение |
|---|---|
| Pi останавливается при запуске с `Tool "edit" conflicts with ...` | Другой пакет тоже регистрирует `edit`. Выберите одного поставщика или используйте `hybrid`; см. [Другой пакет, переопределяющий `edit`](#другой-пакет-переопределяющий-edit). |
| `/offline-doctor` сообщает, что endpoint крошечного исполнителя недоступен | Запустите сервер, затем выполните `/offline-setup` или задайте `PI_OFFLINE_TINY_ENDPOINT`. Переменные окружения перекрывают сохранённую конфигурацию. |
| Сервер отвечает HTTP 500 `JSON schema conversion failed` | Движок один раз повторяет запрос с `json_object`; делать ничего не нужно. |
| `execute_delegated_implementation` отклоняется без UI | Изменения без интерфейса требуют `PI_OFFLINE_ALLOW_HEADLESS_APPLY=1`, только в отдельно изолированном рабочем процессе. |
| Доктор или предварительная проверка сообщают, что MTP активен, но отчёты TRX недоступны | Добавьте `Microsoft.Testing.Extensions.TrxReport` в тестовый проект и восстановите, пока есть сеть. |
| Доктор предупреждает, что `.pi/offline-engine` не игнорируется | Добавьте `/.pi/offline-engine/` в `.git/info/exclude`. |
| pi-knowledge не может скачать модель эмбеддингов | `PI_KNOWLEDGE_OFFLINE=1` задан до первого скачивания; снимите её, проиндексируйте репозиторий онлайн, затем задайте снова. |
| `needs_main_model` | Дешёвый цикл не смог завершиться; прочитайте `reason` и `stage`. Если проверка осталась красной, последний кандидат может всё ещё лежать в рабочем дереве; просмотрите `git diff`. |
| Локальная модель вызывает `line_edit` с пустыми аргументами | Движок уже уплощает эту схему и для `lean`, и для `hybrid` (HE-11); оставшаяся ошибка парсера ik_llama.cpp, отбрасывающая один ведущий пробел значения параметра, описана там и не исправляется в этом пакете. |

## Статус и известные ограничения

Экспериментальный. `pi-offline-engine` имеет версию 0.0.16 и является Git-распространяемым пакетом Pi (`private: true`, не опубликован в npm).

- **Измерено и нет.** Контракт и вспомогательные части покрыты модульными тестами, тестами уровня расширения с поддельным Pi и поддельным TinyCoder и перечисленными выше гейтами. У приёмочного прогона с реальной моделью ([docs/ACCEPTANCE_V0.md](docs/ACCEPTANCE_V0.md)) нет записанного результата, а `docs/HYBRID_EDIT_V0.md` указывает, что для гибридных свидетельств настоящий локальный llama-server не запускался. Поэтому доля успешных реализаций настоящим TinyCoder неизвестна.
- **CI.** Рабочий процесс `.github/workflows/ci.yml` настроен на запуск `gate:local`, аудита production-зависимостей, `gate:pi`, `gate:edit` и `gate:install` при пушах и pull request. Согласно [docs/PROJECT_REVIEW_2026-10-01.md](docs/PROJECT_REVIEW_2026-10-01.md), запуски на хостинге не стартовали, так что гейты запускались только локально. Считайте их проверенными локально, а не проверяемыми CI непрерывно.
- **Проверка только для .NET.** Для других инструментальных цепочек понадобились бы новые раннеры, собираемые движком.
- **Ограничения делегирования.** Не более двух файлов, только `replace_text`/`create_file`, нет операций на уровне символов, нет отката после красной последней попытки, а основная модель должна вручную вставлять исходный код в `context`.
- **Проверка — не смысловая готовность.** Просмотрите diff.
- **Встроенные пакеты** сторонние, закреплённые и загружаются с вашими правами; метрики `pi-lean-edit` привязаны к имени инструмента `edit` и для `line_edit` не проверялись; защита синтаксиса перед записью из `pi-tree-sitter` не проверена вместе с pi-lean-edit.
- **Предложено, но не построено.** Выделение оркестрации из `extensions/index.ts`, MCP-сервер или плагин Claude Code поверх ядра, подключение контекста на стороне движка, подключаемые раннеры проверки и бенчмарк с передовой моделью встречаются только как предложения в обзоре проекта.
